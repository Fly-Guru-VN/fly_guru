# FlyGuru — текущая архитектура

Срез реализации на 4 сентября 2026 года. Этот документ объясняет код, но не
переопределяет его. При расхождении источники проверяются в таком порядке:
`src/` → `supabase/migrations/` → `supabase/seed.sql` → документация.

## 1. Назначение системы

В одном Next.js-приложении живут:

- публичный сайт школы электрофойлов в Нячанге;
- формы заявок и отслеживание источников;
- CRM школы;
- кабинеты сотрудников и агентов;
- Telegram Mini App клиента;
- фоновые задачи, Telegram-уведомления и SMTP-сброс пароля.

Онлайн-оплаты нет. Система фиксирует услугу, способ и дату оплаты, но деньги
принимаются вне сайта.

## 2. Техническая схема

- Next.js App Router и React Server Components;
- server actions для большинства операций кабинетов;
- route handlers в `src/app/api/` для публичных форм, отчётов, cron и Telegram;
- Supabase Postgres как основная БД;
- Supabase Auth для сотрудников и агентов;
- Supabase Storage для фотографий;
- RLS как второй рубеж для пользовательских сессий;
- `service_role` только в серверном коде для контролируемых операций, которым
  недостаточно RLS;
- next-intl: русский без URL-префикса, каркас английского и вьетнамского;
- Vercel, регион `syd1`.

Основные каталоги:

```text
src/app/[locale]/       страницы и server actions
src/app/api/            HTTP endpoints и фоновые задачи
src/lib/                бизнес-правила и доступ к данным
src/components/         общие компоненты интерфейса
src/content/            публичный контент услуг и товаров
supabase/migrations/    эволюция схемы и RLS
scripts/                операции администратора/разработчика
```

## 3. Публичная часть

Основные маршруты:

- `/`, `/training`, `/tandem`, `/club`, `/prices`, `/reviews`, `/contacts`;
- `/shop` и `/shop/[model]`;
- `/r/[code]` — агентский лендинг;
- `/b/[src]` и `/i/[src]` — атрибуционные входы;
- `/login`, `/forgot-password`, `/reset-password`;
- `/member` — Telegram Mini App.

Формы создают `bookings`. Реферальный код и UTM/source сохраняются вместе с
заявкой, а сотрудники продолжают обработку в CRM.

## 4. Роли и доступ

Тип ролей определён в `src/lib/auth.ts`:

| Роль | Домашний раздел | Реальная модель доступа |
|---|---|---|
| `admin` | `/admin` | полный административный доступ |
| `dev` | `/admin` | admin-like доступ, отдельная формула выплаты |
| `instructor` | `/instructor` | клиенты, заявки, занятия, абонементы, смены |
| `mechanic` | `/mechanic` | ограниченные рабочие экраны, смены и расходы |
| `smm` | `/smm` | часть офисных экранов плюс смены/расходы |
| `agent` | `/agent` | только собственная ссылка, статистика и выплаты |
| `member` | `/member` | legacy Supabase-роль; основной кабинет использует Telegram |

`admin` и `dev` считаются admin-like. Для страниц важна роль из таблицы
`users`; JWT используется как быстрый рубеж в `proxy.ts`. Уволенному сотруднику
вход и RLS-доступ закрываются по `left_at`, но исторические сессии и выплаты
сохраняются. Кабинеты и auth-страницы запрещено встраивать в iframe; исключение
только у `/member`, который разрешён внутри `https://web.telegram.org` как
Telegram Mini App.

## 5. Основные процессы

### Заявка и занятие

1. Заявка приходит с сайта, Telegram-кабинета или создаётся сотрудником.
2. Админ подтверждает её; инструктор может принять работу.
3. Занятие создаёт строку `sessions` и связывается с заявкой.
4. Заявка становится `done` либо `cancelled`.
5. Агентская комиссия создаётся только для подходящей услуги и живого агента.

Заявка может быть связана с уже существующей сессией для парного занятия, чтобы
не удваивать выручку и комиссию.

### Клиент и абонемент

- карточка клиента хранится в `clients`;
- абонемент живёт в `subscriptions`;
- остаток = `total_minutes` + корректировки − списания из `sessions`;
- стандартный срок — три месяца от даты продажи;
- списание создаёт сессию с `amount = 0` и `subscription_id`;
- продажа абонемента **не создаёт membership автоматически**;
- membership добавляется администратором вручную.

### Telegram-кабинет клиента

Клиентский бот принимает собственный контакт пользователя и связывает
`telegram_id` с карточкой клиента через `client_telegram`. Mini App проверяет
подпись Telegram `initData` на каждом server action. Сейчас доступны:

- остаток активного абонемента;
- активные записи;
- создание и отмена заявки;
- история занятий.

Supabase password session в этом сценарии не используется.

### Агенты

Админ создаёт агента и его реф-код. Вход в `/agent` выдаётся отдельно скриптом
`scripts/grant-agent-login.mjs`, который привязывает Supabase Auth к уже
существующей строке `users`.

Тарифы находятся в `src/lib/agentTerms.ts`:

- `standard`: гостю скидка 100 000 ₫ за `basic-adult` и 200 000 ₫ за
  `basic-duo`; агенту 200 000 ₫ и 300 000 ₫ соответственно;
- `pct-20`: гостю −5%, агенту 20% фактического чека для тех же услуг.

### Смены и выплаты

Основные константы находятся в `src/lib/salary.ts` и `src/lib/finance.ts`:

- Marina Beach — 35% базы после агентской комиссии;
- CRM — 2% той же базы, поровну между двумя получателями;
- смена по регламенту — 200 000 ₫;
- 15% с занятий распределяются по составу смены дня;
- 15% с оплаченных абонементов формируют котёл;
- СММ — недельный фикс 2 000 000 ₫ плюс предусмотренные кодом доли;
- разработчик — недельный фикс 2 500 000 ₫ плюс предусмотренная доля CRM;
- механик — месячный фикс 10 000 000 ₫.

Точная формула зависит от дат найма/увольнения, открытых смен, payment date и
ручных выплат. Для расчётов источником правды остаются `salary.ts`, `payroll.ts`
и `finance.ts`.

## 6. Данные и миграции

Схема развивается только последовательными файлами
`supabase/migrations/0001…0054`. Миграции 0051–0054 отделяют публичные заметки
от внутренних, закрывают служебные фото клиентов/смен в private Storage и
привязывают путь снимка смены к его строке на уровне БД. Последняя миграция
также отзывает RLS-права уволенного сотрудника даже при ещё живой сессии.
Номер миграции задаёт порядок; пропуск промежуточного файла не поддерживается.

Основные группы таблиц:

- люди: `users`, `clients`, `memberships`, `client_telegram`;
- продажи: `bookings`, `sessions`, `subscriptions`,
  `subscription_adjustments`;
- агенты: `agents`, `ref_visits`, `referral_rewards`, `agent_payouts`;
- работа школы: `shifts`, `shift_photos`, `expenses`, `staff_payouts`;
- справочники: `services`, `payment_methods`, `booking_channels`, `materials`.

`seed.sql` — стандартные услуги для воспроизводимой базы после всех миграций.
Он добавляет отсутствующие строки по уникальному `services.code` и не
перезаписывает уже существующие услуги.

Факт применения миграций к production нельзя определять по репозиторию: его
нужно сверять с самой базой перед деплоем.

## 7. Интеграции и фоновые задачи

- Telegram-бот заявок;
- Telegram-бот отчётов;
- отдельный клиентский бот и webhook `/api/tg`;
- SMTP для восстановления пароля;
- Vercel Cron: напоминания о смене, архивация заявок, истечение абонементов и
  удаление фотографий смен;
- Vercel Analytics.

Секреты перечислены только по именам в `.env.example`. Значения должны жить в
локальном `.env.local` и Environment Variables Vercel.

## 8. Известные несоответствия, которые нельзя забывать

Это описание текущего кода, а не будущих пожеланий:

1. `/member` работает через Telegram, но старый `/invite/[token]` всё ещё
   создаёт password-аккаунт и отправляет туда же. Нужно выбрать одну модель.
2. Unit-тесты есть только у библиотечной логики; API, server actions и RLS не
   покрыты интеграционными тестами.
3. Публичные FAQ и страница клуба говорят, что первый абонемент автоматически
   и навсегда даёт членство, но текущая продажа membership не создаёт: админ
   добавляет его отдельным действием.

Эти пункты должны исчезать из документа только одновременно с соответствующим
изменением кода и тестами.

## 9. Проверка изменений

Минимальный merge-gate:

```bash
npm run lint
npx tsc --noEmit
npm test
npm run build
```

Для денежных, авторизационных и миграционных изменений дополнительно нужны
сценарии разных ролей и проверка на отдельной базе. Нельзя использовать живую
Telegram-группу или production-базу как тестовый стенд без явного согласования.
